# 40 - 制度檔案維護協議

對象：未來要修改 `CLAUDE.md`、`.claude/docs/`、`.claude/agents/` 的任何 session。
原則：**制度檔案是給所有未來 session 用的公共財，改壞的代價由之後每個 session 承擔。寧可少改，不可改壞。**

## 1. 權限分級——哪些可以自己改、哪些要先問使用者

**可自行修改（不必問）**：
- `LESSONS.md`：新增教訓（只增不刪，格式見第 3 節）。
- 修正「已被證實錯誤」的事實：路徑改了、指令失效了、檔案改名了。判準：你有實測證據（指令輸出、ls 結果），而不是「我覺得怪怪的」。
- CLAUDE.md 檔案地圖：repo 新增/刪除了原始檔時同步更新。

**必須先問使用者才能改**：
- 刪除或推翻任何既有規則（禁令、升降級路徑、驗收底線）。規則存在通常有你看不到的歷史原因。
- 更改 agent 定義的 model/effort（這直接影響使用者的花費）。
- 重組檔案結構（改檔名、合併拆分文件）——會弄斷其他檔案裡的交叉引用。
- 動 `prompt.txt`、二進位檔、或任何你不理解用途的檔案。

**灰色地帶的判準**：看「未來 session 的行為」，不是文字的增減。改動使未來 session 多做檢查、多留紀錄 → 通常安全；使未來 session 得以跳過或弱化任何既有步驟（**新增例外條款也算這類**）→ 先問。

## 2. 修改程序（不分大小，一律照做）

1. 備份：`cp <檔案> <檔案>.bak-YYYYMMDD`（同目錄）。commit 後即可刪 .bak——git 歷史已是備份，.bak 不要推上 remote。
2. 修改，然後 read-back 全文一遍：無半截句、無指向不存在的路徑、文內指令實跑過。
3. 交叉引用檢查：`grep -rn "改動的檔名或章節" CLAUDE.md .claude/` 確認沒有別的檔案引用你剛改掉的內容。
4. 單獨 commit（不要跟程式碼改動混在同一個 commit），訊息寫明「改了什麼規則、為什麼」。
5. push。

## 3. 教訓寫回哪裡、用什麼格式

**踩到新坑時**（花超過 3 次工具呼叫才解決的問題、或任何「早知道就好了」的時刻），寫進 `.claude/docs/LESSONS.md`，格式固定三行：

```
## YYYY-MM-DD 一句話標題
坑：發生了什麼（含錯誤訊息關鍵字，方便未來 grep）。
解：怎麼解的／怎麼避開（可執行的指令或判準，不是心得感想）。
```

**什麼值得寫**：環境的意外行為、工具的坑、專案特有的陷阱。
**什麼不要寫**：一次性的任務細節、已在其他制度檔裡的規則（改為在該檔補強）。

## 4. 精簡時機與方法

- **觸發條件**：LESSONS.md 超過 40 條，或 CLAUDE.md 超過 80 行，或任何 docs 檔超過 150 行。
- **方法**：同類教訓合併成一條通則升進對應的制度檔（升進 20-judgment.md 或 CLAUDE.md 禁令區），原條目刪除。精簡是「升級整理」不是「刪掉舊的」。
- 精簡屬於「刪除既有內容」——動手前先問使用者，附上打算合併/刪除的清單。

## 5. 制度健康檢查（順手做，不強制）

如果某條規則你連續多個任務都覺得礙事，不要默默無視它——這正是制度退化的開始。把「哪條規則、為什麼礙事、建議怎麼改」寫進 LESSONS.md 並在回報裡告訴使用者。無視規則和盲從規則一樣糟。
