## 使用者沒問、但我認為對這個環境最重要的三件事

### 1. 制度只有進了 main 才存在

我的所有產出都在 `claude/fable5-system-design-pjm5px` 分支。**未來 session clone 的是 main——如果這個分支沒被 merge，整套制度對它們而言等於不存在。** 我已在收尾總結裡請使用者 merge。如果你是從 main 的 clone 讀到這封信，代表 merge 成功了；如果你是在 claude/* 分支上讀到，merge 可能還沒發生，先跟使用者確認。同樣的邏輯也適用於你：你對制度檔案的任何改進，停在 claude/* 分支上就是白做。改制度的 PR 要明確提醒使用者合併。

### 2. 這個 repo 可能落後於使用者的本機

唯一的 commit 訊息是「Add files via upload」，路徑證據顯示使用者在 Windows 本機（D:/FinalProject/AI）開發，然後手動上傳 GitHub。這意味著：**repo 裡的程式碼可能不是使用者手上最新的版本。** 如果使用者描述的行為跟你讀到的程式碼對不上，優先假設「repo 落後了」而不是「使用者記錯了」，直接問使用者要不要先上傳最新版。在舊碼上做的修改，使用者合併回本機時會很痛苦。

### 3. 這是課程期末專案，取捨標準是「能交、能跑、能展示」

FinalProject 這個名字說明了一切。不要主動提議大重構、引入建置系統、加 CI——除非使用者自己開口。價值排序：修 bug > 加使用者要的功能 > 其他一切。程式碼有些不完美（全域狀態、magic number），在這個情境下是合理的，不要「順手改善」。缺一個 Makefile 和基本測試倒是值得在適當時機「建議」（一句話帶過，使用者要就做），因為它們直接服務「能跑」。

## 這套制度最可能的退化方式與預防

1. **CLAUDE.md 發胖** → 每個 session 都想塞一點東西進去，兩個月後它變成 300 行、每次載入吃掉 context、沒人讀完。預防：40-maintenance.md 設了 80 行上限；新內容進 docs/ 子檔，CLAUDE.md 只加一行路由。守住這個上限比守住任何單一規則都重要。
2. **規則被靜默略過** → 弱模型趕任務時會跳過「派 verifier」「三態標注」這類步驟，且不會說。制度沒有執法者，只有使用者抽查。預防（給使用者，也寫在總結裡）：偶爾檢查回報裡有沒有三態標注、verifier 是否真的跑過；抓到一次就在對話裡糾正，模型會在該 session 內修正。預防（給模型）：40-maintenance.md 第 5 節——覺得規則礙事就寫下來提出，不要默默無視。
3. **驗收儀式化** → verifier 收到「我做了 X，請確認沒問題」這種帶風向的 prompt，就會變成橡皮圖章。預防：30-templates.md 模板 5 的鐵則——verifier 只拿到驗收條件和路徑，拿不到過程敘述。這條被違反時，驗收就已經死了，只是還沒被發現。
4. **LESSONS.md 變垃圾場** → 塞滿一次性細節，真正的坑淹沒其中。預防：三行格式強制執行，40 條觸發精簡。
