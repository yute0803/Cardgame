# 10 - 模型調度守則

適用對象：主對話的模型（不論你是 Sonnet、Opus 還是 Haiku）。
原則一句話：**主對話是指揮官，負責決策與整合；髒活派 subagent，主對話只進結論。**

## 1. 指揮官不下場——什麼工作必須派出去

符合任一條就派 subagent，不要自己在主對話做：

| 情境 | 判準（具體門檻） | 派給誰 |
|---|---|---|
| 大量讀取 | 預計要完整讀 3 個以上檔案，或任何單檔超過 400 行要通讀 | `scout` |
| 掃 repo | 要跨多個檔案找「哪裡有 X」「X 怎麼被用」 | `scout` 或內建 `Explore` |
| 查網頁/文件 | 任何需要 WebSearch / WebFetch 的研究 | `scout`（附上要查的問題清單） |
| 批次改檔 | 同一種修改要套用到 3 處以上 | `worker` |
| 驗收 | 任何「確認做完了沒」的檢查 | `verifier`（見第 6 節） |
| 高風險判斷 | 影響架構、可能破壞既有功能、或你自己不確定的設計決策 | `reviewer` 第二意見 |

反過來說，**這些不要派**（派了反而浪費 token）：讀單一小檔、跑一條指令、改一兩行、git 操作。subagent 冷啟動要重建 context，小事自己做更便宜。

## 2. 派工三件套——每個派工 prompt 必含三段

缺一段就是不合格的派工（模板見 `.claude/docs/30-templates.md`）：

1. **目標與動機**：要做什麼＋為什麼（動機讓 subagent 在細節模糊時能自己做出正確取捨）。
2. **驗收條件**：可勾選的完成判準，例如「gcc 編譯零 error」「回報中每個結論都附 檔案:行號」。不可寫「做好一點」這類抽象語句。
3. **回報格式**：明確規定回什麼、多長。預設：「結論 + 檔案:行號清單，總長不超過 30 行；長產物寫進檔案，只回傳路徑」。

## 3. 模型與 effort 顯式指定

本環境實際可用（已查證，2026-07）：

- **Agent 工具的 `model` 參數**：`haiku`、`sonnet`、`opus`。（`fable` 只在特殊 session 存在，不要依賴它。）
- **`.claude/agents/*.md` frontmatter**：`model:` 同上（另可用 `inherit` 或完整 model id）；`effort:` 可設 `low` / `medium` / `high` / `xhigh` / `max`。effort 只能在 agent 定義檔設定，Agent 工具呼叫時給不了。
- 本 repo 已定義四個 agent（`.claude/agents/`）：

| agent | model | effort | 用途 |
|---|---|---|---|
| `scout` | haiku | medium | 搜尋、讀檔摘要、查文件 |
| `worker` | sonnet | high | 實作、重構、批次修改 |
| `verifier` | sonnet | high | fresh-context 驗收（read-back、編譯、實跑） |
| `reviewer` | opus | high | 第二意見、對抗審查、高風險設計判斷 |

呼叫時 `subagent_type` 填 agent 名稱即可，model/effort 已寫死在定義檔，不必再帶 `model` 參數。

## 4. 回報合約

寫進每個派工 prompt 的固定條款：

- 只回「結論」與「證據指標」（檔案:行號、指令輸出的關鍵行），不要貼整段程式碼或整份文件。
- 產出超過 30 行的內容（報告、清單、diff 說明）一律寫成檔案，回報只給路徑＋三行摘要。
- 明確回報成功/失敗/部分完成，失敗要附：試了什麼、卡在哪、錯誤訊息原文最後 10 行。
- 禁止回「大致沒問題」——沒檢查的部分要明列。

## 5. 升降級路徑

- **haiku 錯一次 → 直接升 sonnet**。不要讓 haiku 重試（重試成本 ≈ 升級成本，但成功率差很多）。
- **sonnet 同一個子任務連錯兩次 → 升 opus**，且派工 prompt 必須附上完整失敗軌跡：兩次各自試了什麼、錯誤訊息、目前檔案狀態。不附軌跡的升級等於重來第三次。
- **opus 解出來之後**：如果同類工作還有剩（例如同樣的修法要套用到其他檔案），把 opus 找到的解法寫成明確步驟，降回 sonnet/haiku 批次套用。
- **升級鏈到 opus 為止，opus 失敗一次就停**。同一子任務的嘗試上限：haiku 最多 1 次、sonnet 最多 2 次、opus 最多 1 次（從哪一級開始都適用，例：sonnet×2 → opus×1 → 停）。停下後把完整失敗軌跡整理給使用者，明說卡住了。這不是失敗，亂燒 token 才是。

## 6. 驗證不自驗

做事的 agent 不能自己宣布做完。驗收一律派 **fresh-context 的 `verifier`**（它沒有做事過程的記憶，只看得到實際成品，所以不會腦補）：

- **檔案類產出**：verifier 用 Read 逐檔 read-back，對照驗收條件逐條勾選。
- **程式碼改動**：verifier 重新編譯（指令在 CLAUDE.md）＋跑 `/tmp/game_cli` 冒煙測試；有單元測試就跑測試。
- **高風險判斷**（架構、演算法正確性）：加派 `reviewer` 第二意見；或讓兩個 agent 各自獨立解一遍，比對答案，不一致就是警訊。
- verifier 的 prompt 只給「驗收條件＋檔案路徑」，**不要給做事過程的敘述**，避免被帶風向。

## 7. Harness 極限（誠實條款）

以上機制補得了「執行品質」：拆解、驗證、重試、多樣本評審都有效。
補不了「品味與模糊題」：例如「這個 UI 配色好不好看」「這兩種遊戲平衡方案哪個好玩」。遇到這類問題：
1. 不要假裝有答案，把選項＋各自的取捨列給使用者選；
2. 或明說「這是品味判斷，我的建議是 X 但信心低」；
3. 絕不把品味判斷包裝成技術結論。
