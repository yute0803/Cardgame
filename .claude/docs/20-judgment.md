# 20 - 判斷力 rubric（弱模型可直接執行）

每條判準都附一個正例（✅ 該這樣）和一個反例（❌ 別這樣）。例子多以本專案為背景。

## 1. 何時該升級模型

**判準**：出現下列任一訊號就升級（升級路徑見 10-delegation.md 第 5 節）：
- 同一個錯誤修了兩次還在（不是兩個不同錯誤，是同一個）。
- 你發現自己在「試試看這樣行不行」而說不出為什麼這樣會行。
- 任務需要跨 3 個以上模組同時推理（例如改牌型判定會連動 score 和 magic）。

✅ 正例：sonnet 兩次嘗試修 `hand_eval.c` 的順子判定，兩次都過了自己寫的測試但 verifier 都找到新反例（A-2-3-4-5 輪子順、同點數多張）。→ 停手，把兩次的 diff、反例、測試輸出整包給 reviewer（opus）。
❌ 反例：haiku 搜尋「PRICE_REDRAW 在哪定義」回錯了位置，主對話又叫 haiku「再找一次，仔細一點」。→ 錯。haiku 錯一次就換 sonnet 或自己 Grep，「仔細一點」不會讓小模型變強。

## 2. 何時算真的完成

**判準**：以下全部成立才能說完成，缺一項就要在回報裡明列：
1. 驗收條件（派工單上的）逐條有 PASS 證據。
2. 程式碼改動：編譯零 error；邏輯層改動另需跑過 `/tmp/game_cli` 冒煙測試或單元測試。
3. fresh-context verifier 檢查過（自己說完成不算數）。
4. 已 commit + push。**push 前不算完成**——container 會回收。

✅ 正例：「score.c 的加倍邏輯已改。驗收：(1) 編譯零 error ✓ (2) 新增 3 個測試案例全過 ✓（輸出見下）(3) verifier 確認 ✓ (4) 已 push，commit abc1234。UI 顯示部分未動。」
❌ 反例：「我已經修改了 score.c 並確認邏輯正確，應該可以正常運作了。」——沒編譯、沒跑、沒 push，「確認邏輯正確」只是把程式碼再讀了一遍。這是本 harness 最常見的假完成。

## 3. 何時該停下來問使用者

**判準**：符合任一條就停下來問，其他情況一律自己決定不要問：
- 動作不可逆且超出任務範圍（刪除/覆蓋不是你建立的檔案、force push、改 main 分支）。
- 兩個合理方案會導致**使用者可感知的不同結果**（遊戲規則、平衡數值、UI 行為），且任務描述看不出偏好。
- 任務前提可能錯了（使用者說「修 X 的 bug」但你查證 X 行為其實正確）。

✅ 正例：使用者說「商店太便宜了，調一下價格」。調成多少是平衡手感問題 → 列出現值（REDRAW 50 / SUIT 80 / PAIR 60）和兩三組建議值，問使用者選哪組。
❌ 反例：使用者說「把順子的加分改成 5 倍」，你跑去問「請問是指 hand_eval.c 裡的順子嗎？」——repo 裡只有一個順子判定，這是查得到的事，問了只是浪費使用者時間。

## 4. 什麼訊號代表方向錯了，該換路而非重試

**判準**（重試是「同方法再來一次」，換路是「承認方法錯了」）：
- 每次修完錯誤，冒出的新錯誤比修掉的多。
- 為了讓方案成立，需要的「例外處理」超過 3 個。
- 你開始想繞過驗收條件而不是滿足它（例如「把這個測試先註解掉」）。
- 連續兩次工具/環境層面的失敗原因相同（例如兩次都卡在裝不了套件）——第三次不會不一樣。

✅ 正例：想在容器裡裝 raylib 來測 UI，apt 被網路政策擋、原始碼編譯缺相依。→ 換路：接受「UI 在此不可測」，改成 code review + 明確告知使用者需在 Windows 實測。
❌ 反例：apt 失敗後接著試 pip、再試手動下載 .so、再試 wine，燒 20 分鐘 token。每次失敗的根因都一樣（網路政策），重試次數不改變根因。

## 5. 品質底線怎麼驗（最低標準，不可再低）

任何程式碼改動的底線 checklist：
- [ ] `gcc -std=c11 -fsyntax-only <改過的每個 .c>` 零 error（UI 檔用不了此法時明說）。
- [ ] 邏輯層改動：CLI 版建置成功＋冒煙跑一輪不 crash。
- [ ] `git diff` 自查一遍：沒有調試 printf 殘留、沒有誤刪別人的程式碼、沒有把二進位加進 staging。
- [ ] 回報中「已實測通過／已編譯未實測／無法在本容器驗證」三態標注正確。

任何文件/制度檔改動的底線 checklist：
- [ ] 改完 read-back 全文一遍，確認沒有半截句子、沒有指向不存在的路徑。
- [ ] 文內引用的檔名、指令，用 ls / 實跑驗證過存在且正確。

## 6. 誠實條款（引用自 00-diagnosis.md，此處是操作版）

- 三態回報：**已實測通過**（有輸出證據）／**已編譯未實測**／**無法在本容器驗證**（說明誰能驗、怎麼驗）。永遠選最保守的那個。
- 不確定的事實：查（scout 派工）→ 查不到就寫「未確認」，禁止用流暢的句子掩蓋沒查證的內容。
- 品味/平衡類問題（好不好玩、好不好看）：明說這是品味判斷，給選項讓使用者決定。模型升級解決不了品味問題。
